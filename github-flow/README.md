# GitHub Flow

## 以部署为中心的开发模式

### GitHub Flow 概要

以部署为中心的开发流程

```text

main⬅️  pull request
⬇️⬇️      ⬆️
branch ➡️
```

### 大致流程

1. main分支时常保持可以部署的状态
2. 进行新的作业时从main分支创建新分支, 新分支名要具有描述性
3. 在第二步新建的本地仓库分支中进行提交
4. 在Github端仓库创建同名分支, 定期push
5. 需要帮助或反馈时创建 Pull Reqest, 以 Pull Request 进行交流
6. 让其他开发者进行审查, 确认作业完成后与 main 分支合并
7. 与 main 分支合并后立刻部署

---

#### 随时部署, 没有发布的概念

该原则遵守流程的第一点规则. 在开发中每隔几个小时进行一次部署, 可以有效防止同事出现多个严重BUG, 但不可避免的小BUG还是会存在.

需要注意的是, 没有经过测试或者测试不通过的代码绝对不可以合并到master分支.

#### 进行新的作业时从main分支创建分支

进行新的作业时要从main分支创建新分支, 无论时添加新功能还是修复BUG. 此外, 新分支名称要具有描述性.

## 简明工作流（补充）

1. 从 `main` 拉取最新代码：`git switch main && git pull`
2. 新建任务分支：`git switch -c feature/<short-desc>`
3. 小步提交并推送：`git add . && git commit -m "feat: ..."`，然后 `git push -u origin <branch>`
4. 在 GitHub 发起 PR，说明变更内容、风险和验证方式
5. 通过 CI 与 Code Review 后合并到 `main`
6. 合并后立即部署，并确认线上状态正常
